title: "Making a busy PostgreSQL database faster without a rewrite"
date: "2026-10-06"
summary: "Three changes that took pressure off PostgreSQL in high-volume lending workflows: fewer repeated lookups, one aggregation instead of many, and indexes built without locking writes."
---

Most database slowness I've dealt with wasn't a clever-query problem. It was the same work done many times, or a safe-looking change that blocked production. Here are the three fixes that paid off most on high-volume Django and PostgreSQL workflows, and how I'd approach each one again.

## 1. Stop looking things up repeatedly

The pattern is easy to write by accident. A loop handles a batch of invoices, and each iteration fetches its related record, or the same reference row, again:

```python
for invoice in invoices:
    customer = Customer.objects.get(pk=invoice.customer_id)
    process(invoice, customer)
```

One query per row is cheap in a test with ten rows and painful with ten thousand. The fix is to load once and reuse.

For related rows, let the ORM join or batch them:

```python
invoices = Invoice.objects.select_related("customer").filter(batch_id=batch_id)
```

For reference data, fetch it once into a dictionary before the loop:

```python
customers = Customer.objects.in_bulk(customer_ids)
for invoice in invoices:
    process(invoice, customers[invoice.customer_id])
```

How to find these: count queries per request or per task rather than reading code. Django's `assertNumQueries` in tests, or query logging in a staging run, shows a query count that grows with the input. A healthy path stays flat as the batch grows.

## 2. Aggregate in the database, once

The second pattern is computing an invoice's status from many pieces of data in several places: one query for paid amounts, another for pending ones, a third in Python to combine them. Each call site repeats the work, and the logic drifts.

Consolidating it into a single aggregation query gives you one place that defines what the status means, and the database does the summing it's good at:

```python
from django.db.models import Sum, Q

Invoice.objects.annotate(
    paid=Sum("payments__amount", filter=Q(payments__status="settled")),
    pending=Sum("payments__amount", filter=Q(payments__status="pending")),
)
```

The performance win is real, but the bigger one is correctness. When status is computed in one query, two screens can't disagree about it.

## 3. Add indexes without blocking writes

A slow query often needs an index, but on a large, busy table a plain `CREATE INDEX` takes a lock that blocks writes while it builds. In a lending system that means stalled operations, which is worse than the slow query.

PostgreSQL's answer is `CREATE INDEX CONCURRENTLY`, which builds the index without blocking writes. It takes longer and has its own rules, but production keeps moving. In Django you can do this with migrations that declare themselves non-atomic:

```python
from django.contrib.postgres.operations import AddIndexConcurrently
from django.db import migrations, models


class Migration(migrations.Migration):
    atomic = False

    operations = [
        AddIndexConcurrently(
            model_name="invoice",
            index=models.Index(fields=["status", "due_date"], name="invoice_status_due_idx"),
        ),
    ]
```

Things to know before relying on it:

- It can't run inside a transaction, hence `atomic = False`.
- If it fails partway it can leave an invalid index behind. Check for one and drop it before retrying.
- It's still extra I/O, so schedule it away from peak load.

## The order I'd do it in

1. **Count queries first.** Repeated lookups are usually the cheapest win and need no schema change.
2. **Consolidate aggregations next.** It improves speed and removes inconsistent definitions.
3. **Index last, and only for queries you've measured.** Every index slows writes a little, so add the ones a real query plan asks for.

For step three, `EXPLAIN (ANALYZE, BUFFERS)` shows whether a query uses an index and where the time goes. Read the plan before adding the index and again after.

## What I'd measure

A before-and-after number makes a change like this believable. Track query count per request or task, p95 latency on the affected endpoints, and lock wait time during migrations. Without those, you only have a feeling that things got faster.
