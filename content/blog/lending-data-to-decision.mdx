title: "From Scattered Financial Data to One Lending Decision"

A lending decision is only as good as the data behind it, and in practice that data arrives from several places that don't agree on format, timing or trust. Most of the engineering in a lending platform isn't the decision itself. It's getting consistent data to the decision, and getting the outcome to the system that acts on it.

This is how I think about that flow, with the systems named by their job rather than their internal names.

## Two Sources of Financial Data

Some businesses have accounting software that syncs automatically. Their invoices, sales and purchase ledgers and transactions arrive without anyone uploading anything.

Others provide ledgers by hand. That data is messier: it has to be extracted, normalized and parsed into transactions before anything can use it.

These are different problems, so they get different components. A **ledger parser** owns manual ledgers. The synced accounting data comes through its own path. Neither one tries to do the other's job.

## Consolidate Before You Analyze

The step that makes the rest tractable is a **consolidation layer** that takes both sources and produces one financial view per business.

```text
Accounting data  ─┐
                  ├─> Consolidation ─> Visibility report
Manual ledger ─> Parser ─┘
```

Downstream code then asks one place for a business's financial picture instead of knowing there are two sources. If a third source appears later, only the consolidation layer changes.

The output is a **visibility report**: an underwriting-oriented summary of the business's activity. It's a product of the data layer, and the underwriting system consumes it rather than rebuilding it.

## Underwriting Combines More Than the Report

The underwriting engine receives the visibility report and the ledger. It then brings in external checks:

- A **credit-bureau check** on credit history.
- A **GSTIN verification** of the business identity and its GST registration and activity.
- A **GST-to-ledger match**, which asks whether the ledger the business provided is consistent with its GST data.

That last check is worth calling out. Each source can look reasonable alone. The useful signal is when they disagree, because a ledger that doesn't line up with GST activity is something an underwriter wants to see.

The engine then produces a decision: approve or reject.

## Hand Off the Approved Case, Not the Whole Pipeline

Approved cases move to the **loan servicing** system, which owns everything after the decision: creating the loan, disbursal, repayment schedules, collections and tracking what's outstanding.

Two things matter about this boundary:

- Servicing receives an approved case. It doesn't need to know how underwriting reached it.
- Underwriting doesn't track repayments. Once it has decided, its job is done.

There's also a second, simpler path: invoice-based disbursal, where an uploaded invoice syncs from the accounting data straight to servicing. It skips the credit-decision flow because it serves a different product. It's worth keeping the two flows distinct in documentation so people don't assume every loan passes through underwriting.

## Ownership Is the Real Architecture

If I had to compress the design into one idea, it's that each system owns one kind of thing:

| System | Owns |
|---|---|
| Accounting sync | Synced financial source data |
| Ledger parser | Manually provided financial data |
| Consolidation layer | The consolidated financial view |
| Underwriting | The credit decision |
| Loan servicing | Disbursal and repayment |

Clear ownership makes the hard operational questions answerable. When a number looks wrong, you know which system to check first. Retries are safer because each step can be repeated without guessing who holds the truth. An audit can follow a decision back through the report to the data it came from.

## Model the Handoffs as Events

Rather than systems reading each other's databases, I prefer to describe each handoff as a business event: a ledger was synced, a visibility report was generated, underwriting passed or failed, a loan was approved, a disbursal completed.

Events give you a few things that direct database access doesn't:

- **A clear contract** between teams, which can change internals without breaking consumers.
- **Idempotency points.** If an event is delivered twice, a consumer can recognise it and do nothing the second time.
- **An audit trail** of what happened and in what order, which is exactly what you want when a decision is questioned later.

## What I'd Watch in Production

- **Reconciliation:** periodically compare consolidated totals against the sources, so drift is found by a check rather than by a customer.
- **Staleness:** know how old the data behind a decision was when the decision was made.
- **Mismatch rates:** track how often the GST-to-ledger match fails, since a sudden change usually points to a data problem upstream rather than a change in borrowers.

None of this is glamorous, but it's what lets a team trust the number at the end.
